## Слайд 2. Как работает сервис: один сквозной поток

**На слайде** — схема из 7 блоков слева направо:

1. **Закупка** — файл «Извещения + ТРУ» (CSV/Excel) или текст

6. **Новые компании** — из открытых реестров, вкладка «Непроверенные»
7. **Выдача** — список, карточка, выгрузка

**Говорим:**

- Поэтому в момент запроса сервис не зависит от капчи ФНС или недоступности ЕИС: всё берётся из базы за миллисекунды.

## Слайд 3. Подбор кандидатов и иерархия ОКПД2

**Заголовок:** Ищем кандидатов тремя путями и учитываем ОКПД2 на четырёх уровнях

**На слайде — три канала:**
- **По коду ОКПД2** — кто побеждал с этими кодами, до 200 кандидатов
- **По заказчику** — кто уже работал с этим заказчиком, сначала в классе ОКПД2 лота, до 100
- **По тексту** — чьи прошлые закупки похожи по описанию (TF-IDF + SVD, косинусная близость), до 100

Каналы объединяются (reciprocal rank fusion) в список до 300 кандидатов. Реальный победитель попадает в этот список в 82% закупок [проверить].

**Таблица уровней ОКПД2** (пример `32.50.13.190`):

| Уровень | Вид кода | Сколько знаков | Вес совпадения |
|---|---|---|---|
| Категория | `32.50.13.190` | 9 цифр — полный код | 1,0 |
| Вид | `32.50.13` | 6 цифр | 0,8 |
| Подгруппа | `32.50.1` | 5 цифр | 0,6 |
| Группа | `32.50` | 4 цифры | 0,4 |
| Класс | `32` | 2 цифры | признаки «заказчик/район в классе» |

**Говорим:**
- Чем глубже совпадение, тем больше вес. Совпадение полного кода весит 1,0, совпадение только группы — 0,4.
- Модель видит победы, участия и долю покрытых позиций отдельно на каждом уровне, поэтому совпадение по группе не равно совпадению по полному коду.
- Класс (2 цифры) используется в признаках «побед у этого заказчика в классе» и «побед у заказчиков того же района в классе».
- Группа (4 цифры, `XX.XX`) — основа статуса «Проверенный» и поиска новых компаний: детальнее реестры не размечены.
- Если код не указан, работают каналы по тексту и по заказчику.

## Слайд 4. Модель ранжирования

**Заголовок:** Модель оценивает пару «закупка × компания» по 33 понятным признакам

**На слайде — доля влияния групп признаков** (SHAP, 180 тыс. пар) [проверить]:
- Опыт и активность компании — 35%
- Совпадение по ОКПД2 — 19%
- История с заказчиком и районом — 18%
- Похожесть описания — 16%
- Соответствие цены (НМЦК в обычном для компании диапазоне) — 9%
- Параметры закупки — 3%

**Внизу:**
- LightGBM LambdaRank, монотонные ограничения: больше побед по коду или у заказчика никогда не понижают оценку.
- Только локальные модели. Внешних API нейросетей нет, эмбеддингов из интернета нет.

**Говорим:**
- Модель училась на апреле–августе 2025, настраивалась на сентябре, проверялась на октябре–декабре.
- Признаки считаются только по истории до даты закупки — утечки из будущего нет.
- Монотонность делает поведение предсказуемым: компания не проиграет из-за того, что у неё больше побед.

## Слайд 6. «Проверенные» и «Непроверенные»: что это значит

**Заголовок:** Две вкладки — две разные задачи

**Слева — «Проверенные»** (44 тыс. компаний с историей закупок СПб 2024–2025):
- Ранжирует модель, оценка 0–100.
- Статус внутри вкладки:
  - **Проверенный** — ≥3 побед в группе ОКПД2 лота (`XX.XX`), последняя не раньше 12 месяцев назад.
  - **Активный участник** — участвовал в этой группе, но побед меньше.
  - **Требует проверки** — есть риск: компания моложе года, выручка упала больше чем вдвое, отрицательный капитал, налоговый долг, массовый адрес или руководитель, недостоверные сведения, РНП в прошлом. Или статус в ЕГРЮЛ не подтверждён.

**Справа — «Непроверенные»** (статус «Новый в пуле»):
- Компании без истории закупок СПб, найдены в открытых реестрах по группе ОКПД2 лота.
- «Непроверенные» = не проверены опытом работы в СПб. Юридически они проверены: действующие, не в РНП.
- Модель их не оценивает: у них нет истории, которую она умеет читать. Порядок задаёт сила доказательства, оценка не выше 75 — ниже кандидатов с историей.

**Внизу — жёсткие фильтры для обеих вкладок:** ликвидированные, компании в РНП и не-МСП в закупке только для МСП в выдачу не попадают.

**Говорим:**
- Вкладки разделены, чтобы новые компании не вытесняли надёжных кандидатов и наоборот. У каждого списка свой топ.
- Статус всегда выводится по правилу, и правило показано рядом со статусом.

## Слайд 10. Роль контрагента и объяснимость

**Заголовок:** Почему компания в списке и почему у неё такая роль — видно в каждой строке

**Слева — правила роли:**
- **Производитель** — основной ОКВЭД 10–32 того же класса, что и лот, или продукция в ГИСП, реестре ПО или медизделий.
- **Дистрибьютор** — ОКВЭД 46 (опт) и/или широкая история: ≥10 разных кодов в классе или ≥30 кодов из ≥5 классов.
- **Поставщик-исполнитель** — остальные: розница, услуги, ремонт, строительство.
- **Уверенность:**
  - высокая — сошлись правило по ОКВЭД и реестр;
  - средняя — сработало одно правило;
  - низкая — роль выведена только из истории.

**Справа — пример строки выдачи** (рамка под скриншот):
- оценка, роль с доказательством («ОКВЭД 46.46; поставлял 37 кодов класса 21»), статус с правилом;
- 2–3 причины из вкладов модели: «Предмет похож на его прошлые контракты (сходство 0,86)», «34 победы в классе у заказчиков того же района»;
- риски: «Не работал с этим заказчиком».

**Говорим:** причины строятся из SHAP-вкладов модели по шаблонам — это реальный вклад признака в оценку, а не выдуманный текст. В карточке видно до 8 факторов и их знак.

## Слайд 12. Масштабирование, ограничения, развитие

**Заголовок:** Готово к развёртыванию и росту

**Масштабирование:**
- Docker Compose: PostgreSQL, API обогащения, сервис, модель.
- API без состояния — масштабируется горизонтально.
- Модель и база реестров пересобираются офлайн и подменяются целиком.
- Обновление реестров — пакетными выгрузками ФНС и ЕИС по расписанию, не поштучно.

**Честные ограничения:**
- В АИС ГЗ мало проигравших в данных — качество там ниже.
- Финансы ИП ФНС не публикует.
- Контакты есть только у компаний с контрактами в ЕИС.

**Развитие:**
- Журнал отклика «подходит / не подходит» для дообучения.
- Интеграция в АИС ГЗ и Электронный магазин через API.
- Подключение ГРЛС для лекарств.

# Ответы на вопросы жюри

### На каком уровне ранжируется ОКПД2? Какими знаками?
- Код ОКПД2 имеет вид `XX.XX.XX.XXX` (9 цифр). Используем 4 уровня совпадения:
  - категория — полный код, 9 цифр, вес 1,0;
  - вид — `XX.XX.XX`, 6 цифр, вес 0,8;
  - подгруппа — `XX.XX.X`, 5 цифр, вес 0,6;
  - группа — `XX.XX`, 4 цифры, вес 0,4.
- Класс (`XX`, 2 цифры) — для признаков «заказчик/район в классе» и правил роли.
- Модель учитывает победы, участия и покрытие позиций на каждом уровне отдельно: точное совпадение весит больше.
- Статус «Проверенный» и поиск новых компаний — по группе (4 цифры): реестры и ОКВЭД детальнее не сопоставляются.
- Если в лоте много кодов, на каждом уровне берутся самые весомые коды лота.

### Откуда обогащение? Что, откуда, зачем, почему?
См. слайд 7. Коротко:
- **ФНС:** ЕГРЮЛ, «Прозрачный бизнес», реестр МСП, ГИР БО, открытые данные о численности, налогах, долгах и штрафах — реквизиты, статус, финансы, риски.
- **ЕИС:** РНП (фильтр), карточки контрактов (контакты).
- **Минпромторг и ГИСП, реестр ПО, Росздравнадзор** — роль «производитель».
- **Портал поставщиков** — профиль новых компаний.

Почему именно они: официальные, бесплатные, без нейросетей (ограничение организаторов). У каждого поля — ссылка и дата.

Почему массовые выгрузки, а не поштучные запросы: у ФНС капча после 6–30 запросов. Выгрузки дают все 44 тыс. поставщиков за часы, и их можно обновлять по расписанию.

### Вопрос про 44-ФЗ и 223-ФЗ
*(Мы точно не помним формулировку. Ниже ответы на вероятные варианты.)*
- **«По какому закону закупки в данных?»**
  - Выгрузка организаторов — закупки заказчиков СПб в АИС ГЗ и Электронном магазине. Это госзаказ по 44-ФЗ: у закупок АИС ГЗ есть реестровый номер ЕИС (заполнен у 70%).
  - Закупки Электронного магазина — малого объёма, в ЕИС отдельным извещением не публикуются, номера нет.
  - Явного поля «закон» в выгрузке нет, модель закон не различает [уточнить у организаторов, если спросят про ЭМ и 223-ФЗ].
- **«Проверяете ли РНП по 223-ФЗ?»** Да. Реестр недобросовестных поставщиков скачан целиком по 44-ФЗ, 223-ФЗ и старому 94-ФЗ. В карточке видно, по какому закону запись и исключена ли она.
- **«Можно ли расширить на 223-ФЗ?»** Да. Сервис не завязан на закон: нужна история закупок 223-ФЗ в том же формате (лот, позиции ТРУ, участники), модель переобучается тем же кодом. Источники обогащения от закона не зависят.
- **Контакты** берём из карточек контрактов 44-ФЗ в ЕИС: там телефон и почта поставщика публикуются обязательно.

### Что значит «Проверенный» и «Непроверенный»?
- **Вкладка «Проверенные»** — компании с историей закупок СПб, ранжирует модель. Статус внутри:
  - **Проверенный** — ≥3 побед в группе ОКПД2 лота за последние 12 месяцев;
  - **Активный участник** — участвовал в группе, побед меньше;
  - **Требует проверки** — есть риск-флаг или статус в ЕГРЮЛ не подтверждён.
- **Вкладка «Непроверенные»** — новые для СПб компании из реестров, статус «Новый в пуле». Не проверены опытом закупок в СПб, но юридически проверены: действующие, не в РНП, активны по налогам и сотрудникам 2025 года.
- Ликвидированные и компании из РНП не попадают ни в одну вкладку.

### Как считается оценка 0–100? [проверить по финальной модели]
- Оценка — место компании среди кандидатов этой закупки: 100 — лучший.
- «Соответствие» 0–100 — насколько компания сильнее реальных победителей похожих закупок: 80 означает, что оценка выше, чем у 80% настоящих победителей.
- У новых компаний оценка не выше 75 и задаётся силой доказательства. Модель их не оценивает.

### Почему модель не оценивает новые компании?
Модель учится на истории участий. У новых компаний её нет, и любая оценка была бы выдумкой. Поэтому для них — прозрачный порядок по доказательствам (уровни A/B/C) и отдельная вкладка.

### Как проверяли качество? Нет ли утечки?
- Сплит по времени: обучение — апрель–август 2025, настройка — сентябрь, тест — октябрь–декабрь.
- Признаки для каждой закупки считаются только по истории до её публикации.
- Демо-лоты октября ранжируются по срезу истории до 1 октября 2025.

### Используете ли нейросети?
Внешних API нейросетей нет. Текст: TF-IDF + SVD, ранжирование: LightGBM — всё локально. Обогащение — парсинг открытых реестров, капчу не распознаём.

### Насколько данные свежие?
- В карточке у каждого поля дата получения.
- Выгрузки ФНС — актуальные на дату скачивания [проверить даты]; реестр МСП в пуле новых — 10.09.2025; реестры Минпромторга и Росздравнадзора — конец сентября 2026.
- Обновление — повторный запуск скриптов загрузки: они идемпотентны.

### Что с ИП?
ФНС не публикует финансы и численность ИП. Для ИП есть статус, МСП, ОКВЭД, РНП, история закупок. Пустые поля так и показываем пустыми.

### Как это масштабируется?
- API без состояния; база PostgreSQL.
- Ответ модели — 1–3 с на закупку, обогащение из базы — миллисекунды.
- Реестры обновляются пакетно, а не по запросу пользователя.
