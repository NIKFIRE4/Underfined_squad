## Зачем это

По ИНН собираем данные о компании из открытых госреестров и пишем их в БД. Эти данные нужны трём потребителям:

| Потребитель | Что берёт | Требование ТЗ |
|---|---|---|
| Ранкер (Data/ML) | витрина `companies` | 6.2 «Компания»: регион, МСП, возраст, выручка, численность |
| Фильтры и статусы | `is_active`, `in_rnp`, `is_smp`, `risk_flags` | ФТ-08; 6.5 «Требует проверки» |
| Карточка контрагента (UI) | `company_facts`: значение + источник + дата | ФТ-07, ФТ-13, НФТ «Достоверность» |

Плюс поиск **новых компаний** по ОКВЭД, которых нет в выгрузке (ФТ-06, статус «Новый в пуле»). Это блок «Обогащение и расширение пула» — 25 баллов из 100.

## Быстрый старт

**Перед запуском положите в `dataset/`** (папка не в git):
- `Поставщики_24-25.csv` — выгрузка организаторов (обязательно);
- `production.xlsx` — РРПП (ПП 719): gisp.gov.ru/pp719v2/pub/prod/ → «Скачать перечень (XLSX)», скриптом сайт отдаёт 403;
- `Экспорт Реестра (Реестр российского ПО) от ….xlsx` — reestr.digital.gov.ru/reestr/ → экспорт XLS.

Без реестров всё работает, но роль «производитель» и поиск новых производителей будут слабее.

```bash
# всё одной командой: выгрузки ФНС → признаки → реестры → история → ГИР БО и РНП (часы, можно прерывать)
docker compose up -d db
docker compose run --rm --entrypoint scripts/enrich_all.sh enrichment
docker compose run --rm -e ENRICH_LIMIT=300 --entrypoint scripts/enrich_all.sh enrichment   # быстрый прогон

# проверка без сети (22 теста, < 1 с); вторая строка — те же тесты на PostgreSQL стенда:
# SQLite не проверяет длину строк и типы, поэтому перед прогоном на стенде гоняйте обе
docker compose run --rm --entrypoint python enrichment -m pytest enrichment/tests -q
docker compose exec db createdb -U squad squad_test   # один раз
docker compose run --rm -e ENRICHMENT_TEST_DB=postgresql+psycopg://squad:squad@db:5432/squad_test \
  --entrypoint python enrichment -m pytest enrichment/tests -q

# отдельные шаги
docker compose up -d db                                         # PostgreSQL 16 + pgvector
docker compose run --rm enrichment enrich 7804428656 --full     # одна карточка с источниками полей
docker compose run --rm enrichment show 7804428656              # карточка из БД, без сети
docker compose run --rm enrichment stats                        # прогресс пакетного прогона

# пакетный прогон по всем ИНН из dataset/Поставщики_24-25.csv, самые активные первыми;
# повторный запуск продолжает с места остановки. Источники лучше гонять отдельными процессами.
docker compose run -d --name enr-bo  enrichment batch --sources bo  --concurrency 2
docker compose run -d --name enr-rnp enrichment batch --sources rnp --concurrency 2

# массовые выгрузки ФНС (файлы в data/fns, около 2,5 ГБ): качаются частями с проверкой CRC
docker compose run --rm enrichment fns-download
docker compose run --rm enrichment fns-load                     # + пул МСП СПб и ЛО для новых компаний
docker compose run --rm enrichment registries-load              # РРПП и реестр ПО из dataset/
docker compose run --rm enrichment history-load                 # история закупок → роль «дистрибьютор» (секунды)
docker compose run --rm enrichment discover 32.50.13.190        # новые компании по ОКПД2 лота
```

**Статус «действующая» для не-МСП — ЕГРЮЛ, отдельно и точечно.** Реестр МСП содержит только действующие компании, поэтому статус известен для 60% поставщиков. Остальные (~17,8 тыс., в основном крупные) проверяются только через ЕГРЮЛ, а он включает капчу: оценка ~4 с на ИНН (не замерено), то есть **~20 ч на всех**. Поэтому:

```bash
# только кандидаты демо-лотов (~500 ИНН, ~30–40 мин) — перед защитой:
docker compose run --rm enrichment batch <ИНН> <ИНН> … --sources egrul --concurrency 1
# все без статуса (~20 ч, можно прерывать и продолжать):
docker compose run -d --name enr-egrul enrichment batch --missing-status --sources egrul --concurrency 1
```

Пока статус не проверен, адаптер ставит кандидату «Требует проверки» и не выдаёт его за действующего.

**Перенос готовой базы** между машинами (вместо повторного многочасового прогона):

```bash
scripts/db_dump.sh                 # → data/enrichment.dump; NO_RAW=1 — без сырых ответов, в разы меньше
docker compose up -d db && scripts/db_restore.sh data/enrichment.dump   # на целевой машине
```

Без Docker: `python3 -m venv .venv && .venv/bin/pip install -r enrichment/requirements.txt`, БД по умолчанию — `sqlite:///data/enrichment.db`. Другую БД задаёт `--db` или переменная `ENRICHMENT_DB`.

## Инварианты (не нарушать)

1. **У каждого поля есть `source` и `fetched_at`** (ТЗ, ФТ-07). Значение без источника в БД не пишем.
2. **Только бесплатные и не нейросетевые источники** (ответ организаторов от 2026-10-01). Коммерческие API (DaData, Checko и т.п.) не используем. Капчу не распознаём, а пережидаем.
3. **Недоступность источника не ломает карточку**: источник получает статус `error` или `captcha` в `enrichment_runs`, карточка — `enrichment_status = partial`, догрузка — повторным `batch`.
4. **Сырые ответы сохраняем** (`raw_responses`), чтобы перепарсить без сети.
5. **Лимиты частоты соблюдаем.** ФНС включает капчу быстро; бан посреди демо недопустим.
6. ИНН проверяем по контрольной сумме до запроса.

## Как устроено

```
enrichment/
  sources/{egrul,pb,rmsp,bo,rnp}.py   клиент источника: fetch(http, inn) -> SourceResult(facts, raws)
  fns_dumps.py                        потоковый разбор выгрузок ФНС → те же факты
  http.py                             httpx, лимитер на источник, повторы, пауза и замедление на капче
  pipeline.py                         все источники по ИНН параллельно; ошибка источника не роняет карточку
  card.py                             выбор значения по приоритету источников, расхождения, флаги риска
  registries.py                       РРПП и реестр ПО из XLSX
  discovery.py                        новые компании по ОКПД2 лота (ФТ-06) и роль (ТЗ 6.4)
  tests/                              офлайн-тесты на сохранённых реальных ответах
  storage.py                          SQLAlchemy Core: SQLite или PostgreSQL
  __main__.py                         CLI
```

**Таблицы:**
- `raw_responses` — сырые ответы источников;
- `company_facts` (inn, field, source → value, fetched_at) — одно поле из одного источника;
- `enrichment_runs` (inn, source → ok | error | captcha);
- `companies` — витрина, пересобирается из фактов (`python -m enrichment rebuild`).

Карточку для UI с источником, датой и расхождениями по каждому полю отдаёт `card.resolve()` (CLI: `show`).

## Новые компании и роль

`discovery.find_new_companies(engine, okpd2, regions={"78","47"}, exclude=<ИНН из истории>)` — кандидаты без истории со скором 0–100 и доказательствами:

| Канал | Совпадение | Скор |
|---|---|---|
| РРПП, реестр ПО | ОКПД2 продукции: полный код / 3 / 2 / 1 уровень | 60 / 50 / 40 / 20 |
| Продукция в реестре МСП | то же | на 5 меньше |
| ОКВЭД в реестре МСП | основной / дополнительный по первым 4 знакам (XX.XX) | 35 / 20 |
| Бонусы | регион лота +10; совпало больше одного канала +10 | ≤ 100 |

Производителей из реестров берём из любого региона, остальных — только из регионов лота.

`discovery.classify_role(company, lot_okpd2)` — роль по ТЗ 6.4:
- **производитель / правообладатель** — ОКВЭД 10–32 того же класса, что лот, или запись в РРПП, реестре ПО или продукции МСП; уверенность high, если сработали оба правила;
- **дистрибьютор** — ОКВЭД 46 и/или широкий ассортимент в истории закупок (`history-load`): ≥ 10 разных ОКПД2 в классе лота или ≥ 30 кодов из ≥ 5 классов (медиана по поставщикам — 1 код, 90-й перцентиль — 12). Уверенность high — ОКВЭД 46 и история; medium — одно правило; low — только история;
- **поставщик-исполнитель** — ОКВЭД 47, 33 и сервисные разделы; без ОКВЭД — по истории участий с уверенностью low.

Доказательства — фразы для карточки: «Основной ОКВЭД 46.46 — …», «Участвовал в лотах с 37 разными кодами ОКПД2 класса 21», «Найден в реестре промышленной продукции (ПП 719): ОКПД2 32.50.13.190».

## Подключение к web-service

Адаптер под контракт `web-service/INTEGRATION.md` (ветка `web-service-mvp`) — [enrichment/webservice.py](../../enrichment/webservice.py). Файл `web-service/integrations/enricher.py` целиком:

```python
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[2]))  # корень репозитория с пакетом enrichment
from enrichment.webservice import READY, enrich  # noqa: E402,F401
```

Что делает `enrich(lot, candidates)`:
1. Берёт карточки кандидатов из БД (`ENRICHMENT_DB`). Если `ENRICH_LIVE=1`, ИНН, которых нет в БД, дозапрашивает с общим таймаутом `ENRICH_LIVE_TIMEOUT` (15 с).
2. Исключает ликвидированных, кандидатов из РНП и, при `is_smp=true`, не-МСП. Если данных нет, ставит «Требует проверки» и «Не обогащено».
3. Заполняет имя, КПП, регион, МСП, роль; статус «Требует проверки» с флагами риска; 2–4 причины; `sources` с URL источника и датой получения.
4. Добавляет до `ENRICH_NEW_MAX` (10) новых компаний по ОКПД2 лота: статус «Новый в пуле», скор контентного канала, приведённый к шкале ≤ 75, чтобы новые не вытесняли сильных кандидатов с историей.

Зависимости web-service ставятся из `enrichment/requirements.txt`. Модели нейросетей не используются.

## Флаги «Требует проверки» (`companies.risk_flags`)

Каждый флаг — это `{code, text}`, а `text` можно сразу показывать как причину. Пороги заданы константами в [card.py](../../enrichment/card.py).

| code | Правило | Источник |
|---|---|---|
| `young` | моложе 1 года | ЕГРЮЛ, ПБ |
| `revenue_drop` | выручка упала больше чем на 50% | ГИР БО или налоговая отчётность |
| `negative_equity` | капитал < 0 | ГИР БО |
| `invalid_info`, `invalid_person` | недостоверность сведений о компании, руководителе или учредителе | ПБ |
| `tax_debt` | недоимка > 1000 ₽ | `debtam`, ПБ |
| `no_taxes` | налоги = 0 при выручке > 10 млн ₽ | `paytax` + ГИР БО |
| `no_reporting` | не сдаёт отчётность больше года | ПБ |
| `mass_address`, `mass_director` | массовый адрес; руководитель в ≥ 5 компаниях | ПБ |
| `rnp_history` | раньше был в РНП, сейчас исключён | РНП |

Жёсткие фильтры — отдельные колонки: `is_active = false` и `in_rnp = true`.
