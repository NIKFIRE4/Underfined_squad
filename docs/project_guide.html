Сервис подбора контрагентов — гид для команды

Всё, что нужно знать перед защитой: как устроен сервис, откуда данные, какие цифры и что отвечать. Состояние на 02.10.2026. Цифры модели берутся из models/meta.json: если загрузим новую модель, сверить их со слайдами 1, 4 и 5.

1. Коротко

На вход — закупка: файл «Извещения + ТРУ» в CSV или Excel либо JSON в API. На выход — два списка компаний.

  • Проверенные — компании с историей закупок в СПб. Ранжирует обученная модель.
  • Непроверенные — новые для СПб действующие компании из открытых реестров.

У каждой компании есть оценка, роль, статус, причины, риски, контакты и источник с датой для каждого факта.

69,3%победитель в топ-10
37,7%победитель на 1-м месте (бейзлайн 10,9%)
14открытых государственных источников
148 тыс.действующих новых компаний СПб и ЛО
0внешних нейросетей

2. Что было → что стало

Было: задача и черновик ТЗ

  • Три CSV организаторов: 604 тыс. извещений, 3 млн позиций ТРУ, 1 млн записей участников, 44 тыс. ИНН.
  • В ТЗ планировались эмбеддинги e5/bge-m3, Redis и RQ для очереди, React-интерфейс.
  • Обогащение планировали поштучными запросами в ЕГРЮЛ.
  • Интерфейс сначала работал в деморежиме с вымышленными компаниями.

Стало: работающий сервис

  • Модель: LightGBM LambdaRank, 33 признака, честный временной сплит, причины из SHAP.
  • Текст: TF-IDF + SVD — быстро на CPU, без весов нейросетей.
  • Обогащение: заранее собранная база из 14 источников вместо поштучных запросов: капча ФНС не мешает, ответ за миллисекунды.
  • Расширение пула: 148 тыс. проверенных на активность компаний в PostgreSQL, привязанных к группам ОКПД2.
  • Интерфейс: на чистом JS без сборки — загрузка файлов, две вкладки, карточка, выгрузка CSV/XLSX по лоту.

Важные особенности

  • АИС ГЗ: около одной записи участника на лот — виден в основном победитель. В ЭМ — 2,7 записи на лот. Поэтому метрики считаем по площадкам отдельно.
  • reqnum заполнен у 70% лотов АИС ГЗ и пуст в ЭМ. Это ключ для перехода в ЕИС: по нему мы находим контракты и контакты.
  • Длинный хвост: 38% поставщиков победили ровно один раз. Отсюда нужда во внешних реестрах.
  • НМЦК от нуля до 4·10¹⁰ ₽: логарифмируем, нули считаем пропуском.
  • ИНН: около 36 нестандартной длины, часть потеряла ведущие нули в Excel. Проверяем контрольную сумму, ведущие нули восстанавливаем.

5. Пайплайн целиком

Сервис состоит из двух контуров. Офлайн заранее готовит модель и базу компаний. Онлайн отвечает на запрос за секунды и в интернет не ходит.

Офлайн: подготовка (делается один раз, потом по расписанию)

  1. Очистка данных (01_eda_preprocessing.ipynb, ~8 мин). Проверка ИНН, нормализация ОКПД2 по уровням, лемматизация названий, логарифм НМЦК. Результат — Parquet.
  2. Профили поставщиков на каждый месяц (recsys/profiles.py). Победы и участия по уровням ОКПД2, заказчики, районы, ценовой коридор, давность. Строго по данным до среза — без утечки из будущего.
  3. Текстовая модель (recsys/text.py). TF-IDF + SVD по лотам, центроид прошлых лотов каждого поставщика.
  4. Обучение ранкера (02_ranker.ipynb, ~1 ч). Обучение — апрель–август 2025, настройка — сентябрь, тест — октябрь–декабрь. Результат — models/ranker.txt, калибровка «Соответствия» — fit_calibration.json.
  5. Массовые выгрузки ФНС (fns-download, fns-load). Реестр МСП (2,1 ГБ), численность, уплаченные налоги, недоимки, штрафы. Скачиваются частями с проверкой CRC: битый архив не ломает прогон.
  6. Реестры производителей (registries-load): ГИСП/ПП 719 и реестр российского ПО. История (history-load): широта кодов и число заказчиков — для роли дистрибьютора.
  7. Поштучные источники (batch). ГИР БО (финансы), «Прозрачный бизнес», ЕГРЮЛ; контакты из карточек контрактов ЕИС. Отдельно реестр РНП целиком (rnp-dump). Есть лимиты частоты, паузы при капче и HTTP 429, продолжение с места остановки.
  8. Витрина карточек (rebuild). Из таблицы фактов «ИНН — поле — источник — значение — дата» собирается карточка: приоритет источников, расхождения, флаги риска, роль, сведения раньше 2024 года отбрасываются.
  9. Пул новых компаний (pool-activity → scripts/build_unverified_pool.py). МСП СПб и ЛО без истории в выгрузке, отфильтрованные по активности в 2025 году и привязанные к группам ОКПД2 с доказательством.
  10. Дамп базы (scripts/db_dump.sh) → Яндекс Диск → на стенде db_restore.sh или db_merge_ydisk.sh.

Онлайн: что происходит, когда пользователь загрузил закупку

  1. Приём файлов (web-service/server.py, inputs.py). CSV или Excel; тип таблицы определяется по столбцам; UTF-8 или 1251; разделитель ; или ,. Проверки: дубликаты lot_id, ТРУ без извещения, пустые строки.
  2. Сборка лота (pipeline.py). Извещение + позиции ТРУ → объект Lot.
  3. Кандидаты (recsys/candidates.py). Три канала — по коду ОКПД2 (до 200), по заказчику (до 100), по тексту (до 100) — объединяются через reciprocal rank fusion в список до 300 кандидатов. Победитель попадает в него в 82% закупок.
  4. Признаки (recsys/features.py). 33 признака пары «лот × кандидат»: опыт, ОКПД2 по уровням, заказчик и район, текст, цена, контекст лота.
  5. Ранжирование и объяснение (recsys/inference.py, explain.py). Оценка модели, место 0–100, «Соответствие», статус по правилу, 2–3 причины и риски из SHAP-вкладов.
  6. Обогащение (integrations/enricher.py → enrichment-api :8010). Пакетом по ИНН из базы: название, регион, МСП, роль, финансы, флаги риска, источники. Жёсткие фильтры: ликвидирован, в РНП, не МСП при закупке «только для МСП» — убираем из выдачи.
  7. Новые компании (integrations/new_pool.py). Из PostgreSQL берутся компании, у которых группа ОКПД2 (XX.XX) совпадает с позициями лота. Порядок — по силе доказательства, оценка не выше 75. При закупке «только для МСП» — только МСП.
  8. Результат. Сводка, лоты, вкладки, карточка компании (/api/suppliers/{inn}/card), выгрузка CSV и CSV/XLSX по одному лоту.

Если API обогащения или база недоступны, модель всё равно отдаёт выдачу. Строки помечаются «источник недоступен — требуется проверка», вкладка новых компаний пуста. Сервис не падает.

API для интеграции

  • POST /api/recommendations (веб-сервис, :8000) — одна закупка в JSON → топ поставщиков с причинами и факторами.
  • GET /api/suppliers/{inn} (обогащение, :8010) — полная карточка; ?offline=true — только из базы, ?refresh=true — перезапросить источники.
  • POST /api/suppliers/batch — карточки пакетом; /docs — Swagger; /progress — прогресс сбора данных.

Модель видит победы, участия и долю покрытых позиций лота на каждом уровне отдельно. Поэтому точное совпадение кода весит больше совпадения группы. Если у лота много кодов, на каждом уровне берутся самые весомые. Если кода нет, работают каналы по тексту и по заказчику.

Монотонность: рост числа побед по коду или у заказчика никогда не понижает оценку. Модель ведёт себя предсказуемо и не «наказывает» за опыт.

Оценки в выдаче:

  • score 0–100 — место среди кандидатов лота;
  • «Соответствие» 0–100 — оценка выше, чем у такой доли реальных победителей. Пример: «80» значит, что сильнее 80% настоящих победителей.

Принципы

  • Факт с паспортом. Каждое значение хранится вместе с источником и датой получения. В карточке это видно у каждого поля; расхождения источников показываются.
  • Только бесплатное и без нейросетей. Так ответили организаторы. Капчу не распознаём: при капче — пауза и замедление.
  • Повторяемость. Все шаги можно перезапустить: продолжают с места остановки и не дублируют данные.
  • ИП: ФНС не публикует финансы и численность ИП. Такие поля пустые, мы их не выдумываем.

Флаги риска → статус «Требует проверки»

Моложе года · выручка упала более чем на 50% · отрицательный капитал · недостоверные сведения в ЕГРЮЛ · налоговая недоимка · нет уплаченных налогов · нет отчётности · массовый адрес · массовый руководитель · запись в РНП в прошлом.

8. Новые компании (расширение пула)

  1. Кандидаты. Компании из реестра МСП ФНС (свежий снимок) с регистрацией в СПб и ЛО. Сюда не входит никто из 44 тыс. ИНН выгрузки.
  2. Проверка, что компания жива. Юрлицо считается активным, если в 2025 году платило налоги или имело сотрудников. ИП — если есть лицензии или продукция в реестре. Исключаются ликвидированные, компании из РНП и уже известные поставщики. У каждого исключения записана причина.
  3. Итог: 148 тыс. в пуле, 316 тыс. отсеяно. Уровни: strong 39 тыс. (налоги и от 5 сотрудников), active 106 тыс., signal 3 тыс. (ИП с лицензиями или продукцией).
  4. Привязка к ОКПД2 (build_unverified_pool.py). Связи ОКВЭД → группа ОКПД2 выучены по победителям выгрузки (lift, число и доля побед) плюс прямое совпадение кода. Добавляются коды продукции из реестра МСП и доказательства из госконтрактов, реестров производителей и лицензий.
  5. Выдача для лота. Сначала сильное доказательство (контракты в группе, реестр, лицензия, совпадение основного ОКВЭД), затем ассоциация по ОКВЭД. Внутри — уровень пула, налоги, численность. Оценка не выше 75.

Ретропроверка прежнего пула на 01.10.2025: на каждые 10 тыс. компаний уровня A (госконтракты + СПб/ЛО) — 181 будущий победитель закупок СПб, у уровня C — 17. Значит, порядок по силе доказательства работает.

Роли

  • Производитель — основной ОКВЭД 10–32 того же класса, что и лот, или продукция в ГИСП, реестре ПО или медизделий.
  • Дистрибьютор — ОКВЭД 46 (опт) и/или широкая история: ≥10 разных кодов в классе или ≥30 кодов из ≥5 классов.
  • Поставщик-исполнитель — остальные: розница, услуги, ремонт, строительство.
  • Уверенность: высокая — сошлись ОКВЭД и реестр; средняя — одно правило; низкая — роль выведена только из истории. Доказательство показывается рядом с ролью.

Победитель в 11,6% закупок не попадает в список кандидатов. Чаще всего это новые для СПб компании — ровно их закрывает вкладка «Непроверенные».

Покрытие обогащения у поставщиков-юрлиц: статус 94%, ОКВЭД 93%, выручка 92%, численность 88%, возраст 83%, РНП 100%.

11. Ограничения — говорим честно

  • В АИС ГЗ в данных почти нет проигравших участников — учиться модели там сложнее, качество ниже.
  • Финансов и численности ИП ФНС не публикует.
  • Контакты есть только у компаний, у которых есть контракты 44-ФЗ в ЕИС (у новых компаний — по госконтрактам из выгрузки пула).
  • Связь ОКВЭД → ОКПД2 — наш вывод по данным, а не данные реестра. Поэтому у каждой связи показано доказательство.
  • Точность роли на ручной выборке мы не мерили — делали выборочную проверку.
  • Журнала отклика «подходит / не подходит» пока нет.

12. Вопросы организаторов и жюри

На каком уровне ранжируется ОКПД2? Сколько знаков?

На четырёх уровнях: группа (4 цифры, 32.50, вес 0,4), подгруппа (5 цифр, 0,6), вид (6 цифр, 0,8), полный код (9 цифр, 1,0). Плюс класс (2 цифры) — в признаках заказчика и района. Статус «Проверенный» и поиск новых компаний — по группе: реестры и ОКВЭД точнее не сопоставляются.

Вопрос про 44-ФЗ и 223-ФЗ
  • Закон в данных. В выгрузке нет поля с законом. АИС ГЗ — госзаказ СПб по 44-ФЗ: у 70% лотов есть номер ЕИС. ЭМ — закупки малого объёма, в ЕИС отдельным извещением не публикуются.
  • РНП. Проверяем по 44-ФЗ, 223-ФЗ и 94-ФЗ, реестр скачан целиком. В карточке видно закон и состояние записи.
  • Расширение на 223-ФЗ. Сервис от закона не зависит: нужна история закупок в том же формате, модель переобучается тем же кодом.
  • Контакты — из контрактов 44-ФЗ: там телефон и почта поставщика публикуются обязательно.
Что значит «проверенный» и «непроверенный»?

Это про опыт в закупках СПб, а не про юридическую чистоту. «Проверенные» — есть история, ранжирует модель. «Непроверенные» — новые для СПб, но действующие, не в РНП, платили налоги в 2025 году. Внутри «Проверенных» есть статусы «Проверенный», «Активный участник», «Требует проверки» — у каждого показано правило.

Откуда данные о компаниях? Законно ли парсить?

Только открытые государственные источники, бесплатные. В основном — официальные открытые выгрузки ФНС (раздел «Открытые данные»), реестры Минпромторга, Минцифры, Росздравнадзора и публичные страницы ЕИС. Капчу не обходим, частоту запросов ограничиваем. Платные агрегаторы не используем.

Нет ли утечки данных в метриках?

Нет. Сплит по времени: тест — октябрь–декабрь 2025. Признаки для каждой закупки считаются только по истории до её публикации. Демо-лоты октября ранжируются по срезу истории до 1 октября 2025.

Почему LightGBM, а не нейросеть? Почему не эмбеддинги?

Нейросетевые API запрещены. Локальные эмбеддинги разрешены, но TF-IDF + SVD на 3 млн позиций считается за минуты на CPU, а текстовый признак уже самый сильный. LightGBM на табличных признаках — стандарт для ранжирования. Он быстрый, монотонные ограничения делают его объяснимым, SHAP даёт причины.

Почему в АИС ГЗ качество ниже?

В данных АИС ГЗ видно в основном только победителя: проигравших нет, учиться различать сильных и слабых сложнее. Мы показываем метрики по площадкам отдельно, и бейзлайн превзойдён на обеих.

Как масштабировать?

API без состояния, PostgreSQL. Модель и база реестров пересобираются офлайн и подменяются целиком. Реестры обновляются пакетными выгрузками по расписанию. На закупку — 1–3 с, карточка из базы — миллисекунды.

Насколько свежие данные?

У каждого поля дата получения. Выгрузки ФНС и реестров — сентябрь–октябрь 2026. Сведения старше 2024 года в карточку не попадают. Обновление — повторный запуск тех же скриптов.

Почему новые компании не оценивает модель?

Модель учится на истории участий, а у новых её нет — любая оценка была бы выдумкой. Поэтому у них прозрачный порядок по силе доказательства и отдельная вкладка с оценкой не выше 75.

Как проверить, что роль определена верно?

У роли всегда есть доказательство («ОКВЭД 46.46; поставлял 37 кодов класса 21») и уровень уверенности. Систематическую ручную разметку мы не делали — это следующий шаг. Правила открыты и проверяются по карточке.

Что если источник недоступен?

Выдача не ломается: данные берутся из базы, а без базы модель работает одна, с пометкой «требуется проверка». В API есть режим offline — только база, без интернета.

13. Вопросы заказчиков (контрактных управляющих)

Могу ли я доверять списку?

Каждая строка объяснена: почему компания в списке, по какому правилу у неё статус, откуда каждый факт и на какую дату. Ликвидированные и компании из РНП в список не попадают. Риски показаны явно.

Как связаться с компанией?

В карточке — телефон, почта и почтовый адрес из её контрактов в ЕИС, ссылка на контракт, а также ссылки на ЕГРЮЛ, ГИР БО и ЕИС.

Зачем мне это, если закупка всё равно открытая?
  • Найти тех, кому направить запрос ценовой информации при обосновании НМЦК.
  • Понять, есть ли на рынке конкуренция по позиции.
  • Заранее увидеть рискованных участников.

Сервис расширяет круг компаний, а не ограничивает его.

Почему компании X нет в списке?

Возможные причины: она ликвидирована или в РНП; не МСП при закупке «только для МСП»; нет побед и участий по кодам лота. Или она ниже в списке — выгрузка содержит всех кандидатов, а не только видимый топ.

Можно без кода ОКПД2?

Да: работают каналы по тексту предмета и по заказчику. С кодом точнее.

Что такое «Соответствие 80»?

Оценка компании выше, чем у 80% реальных победителей похожих закупок. Это не вероятность победы, а сила кандидата.

Можно выгрузить в Excel?

Да. Вся выдача — в CSV, отдельный лот — в CSV или XLSX с причинами, статусами и источниками.

Как часто обновляются данные? Сколько ждать ответа?

Реестры — пакетно по расписанию, у каждого поля видна дата. Ответ — секунды на закупку.

Интеграция с АИС ГЗ / ЭМ?

Есть HTTP API: POST /api/recommendations для выдачи и GET /api/suppliers/{inn} для карточки. Swagger описан, встраивание — через вызов из карточки закупки.

14. Речь по слайдам (преза.pptx)

Примерно 6–7 минут. Говорим своими словами, цифры — точно как на слайдах.

Слайд 1 · Титул ~25 с

Мы — команда Undefined squad. Наш сервис принимает закупку и возвращает ранжированный список поставщиков, производителей и дистрибьюторов. Для каждого видно роль, статус, причины и источник каждого факта. Три цифры для старта: в 69% закупок реальный победитель есть в первых десяти строках. Первое место мы угадываем в два с половиной раза чаще базового правила. Данные — из 14 открытых государственных источников, без нейросетей.

Слайд 2 · Сквозной поток ~30 с

Как это работает. Пользователь загружает извещения и позиции — в CSV или Excel. Модель ранжирует кандидатов из истории по 33 признакам. Затем каждую компанию мы обогащаем из нашей базы реестров и отсекаем ликвидированных, недобросовестных и не-МСП, если закупка только для МСП. Параллельно из реестров подбираются новые для СПб компании. На выходе — список, карточка и выгрузка. Ответ — одна–три секунды. Важно: все реестры мы скачали заранее, поэтому в момент запроса сервис не зависит ни от капчи ФНС, ни от доступности ЕИС.

Слайд 3 · Кандидаты и ОКПД2 ~40 с

Кандидатов ищем тремя путями: кто побеждал с этими кодами, кто уже работал с этим заказчиком и чьи прошлые закупки похожи по тексту. Объединяем — до 300 кандидатов на лот. Про ОКПД2: код девятизначный, и мы сравниваем его на четырёх уровнях — группа (четыре цифры), подгруппа, вид и полный код. Чем глубже совпадение, тем выше вес: от 0,4 за группу до единицы за полный код. Модель видит победы и участия на каждом уровне отдельно. Класс из двух цифр используем для истории с заказчиком и районом и для роли.

Слайд 4 · Модель ~30 с

Модель — LightGBM в режиме ранжирования. Она оценивает пару «закупка — компания». Больше всего решают опыт компании, совпадение по ОКПД2, история с заказчиком и районом и похожесть описания; цена и параметры лота — меньше. Модель монотонная: больше побед никогда не понижают оценку, поэтому поведение предсказуемо. Всё работает локально, внешних нейросетей нет.

Слайд 5 · Качество ~45 с

Проверяли честно: модель училась до августа 2025 года, а тестировалась на 88 тысячах закупок октября–декабря, которых не видела. Зачёт строгий — засчитываем только фактического победителя. Бейзлайн из ТЗ, «самые частые победители по коду», ставит победителя первым в 11% закупок. Наша модель — в 38%. В топ-10 — 69% против 39%. По MRR и NDCG тоже кратный рост. Модель выигрывает на обеих площадках. В АИС ГЗ чуть ниже, потому что там в данных почти нет проигравших участников.

Слайд 6 · Проверенные и непроверенные ~40 с

В выдаче две вкладки. «Проверенные» — 44 тысячи компаний с историей закупок в СПб, их ранжирует модель. Внутри три статуса по прозрачным правилам. «Проверенный» — три и более победы в группе ОКПД2 лота за последний год. «Активный участник» — участвовал, но побед меньше. «Требует проверки» — есть риск: молодая компания, падение выручки, долги, массовый адрес. «Непроверенные» — это компании без опыта в СПб, но юридически проверенные: действующие, не в РНП, в 2025 году платили налоги. Модель их не оценивает, у них нет истории. Поэтому они идут отдельным списком и не вытесняют надёжных кандидатов.

Слайд 7 · Источники ~40 с

Карточку собираем из 14 открытых государственных источников. ЕГРЮЛ — статус и возраст. Реестр МСП — категория и фильтр для МСП-закупок. ГИР БО — финансы. Открытые данные ФНС — численность, налоги и долги. РНП — недобросовестные поставщики. Контракты ЕИС — телефоны и почты. Реестры Минпромторга, Минцифры и Росздравнадзора — производители. Всё бесплатно. Основную часть берём массовыми выгрузками ФНС: поштучно ФНС закрывает доступ капчей.

Слайд 8 · Достоверность ~30 с

Мы храним не готовую карточку, а факты: какое поле, из какого источника и на какую дату. Если источники расходятся, видно оба значения. Реестр РНП скачан целиком — 126 тысяч записей, проверка мгновенная. Если какой-то источник упадёт, выдача не сломается. Покрытие юрлиц: статус и ОКВЭД — больше 90%, выручка — 92%, РНП — 100%.

Слайд 9 · Расширение пула ~40 с

Теперь главное для расширения конкуренции. Мы взяли полмиллиона компаний вне выгрузки: из реестра МСП, реестров производителей, лицензий и госконтрактов других регионов. Каждую привязали к группам ОКПД2 с доказательством. Затем очистили по свежим данным ФНС 2025 года: оставили только тех, кто платил налоги или имел сотрудников. Так ушло 316 тысяч пустышек и ликвидированных. Осталось 148 тысяч действующих компаний Петербурга и Ленобласти. Сильнее те, у кого есть госконтракты и реестровые записи. Ретропроверка: среди них в десять раз больше будущих победителей, чем среди слабых.

Слайд 10 · Роли и объяснимость ~30 с

Роль определяется правилами. Производитель — профильный производственный ОКВЭД или продукция в реестре. Дистрибьютор — оптовый ОКВЭД или очень широкая история кодов. Остальные — исполнители. У роли есть уверенность и доказательство. Причины в строке выдачи — реальные вклады признаков модели, переведённые в понятные фразы. Например: «предмет похож на его прошлые контракты» или «34 победы в этом классе у заказчиков района».

Слайд 11 · Интерфейс и демо ~60 с с показом

Покажем вживую. Загружаем файл закупки — тип таблицы сервис определяет сам. Открываем выдачу: лоты, две вкладки, у каждой строки оценка, роль, статус и причины. Открываем карточку: реквизиты, руководитель, финансы по годам, история в СПб, риски, контакты и у каждого поля источник с датой. Выгружаем лот в Excel.

Демо: лот медизделий → карточка из «Непроверенных» → закупка только для МСП → выгрузка XLSX.

Слайд 12 · Масштабирование и развитие ~30 с

Сервис поднимается в Docker. API без состояния и масштабируется горизонтально. Модель и база реестров пересобираются офлайн и подменяются целиком, реестры обновляются пакетами по расписанию. Честно об ограничениях: в АИС ГЗ мало проигравших, финансов ИП ФНС не публикует, контакты есть только у тех, у кого были контракты в ЕИС. Дальше — журнал отклика для дообучения, интеграция в АИС ГЗ и Электронный магазин через API и подключение ГРЛС для лекарств. Спасибо, готовы ответить на вопросы.
